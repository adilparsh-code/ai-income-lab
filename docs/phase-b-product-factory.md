# Phase B — Opportunity → Real Product Factory

Status: **CODE COMPLETE** (all gates green). Publishing, payment, traffic, and
revenue remain **future capabilities** — nothing in this phase activates or
pretends them.

## What Phase B adds

A durable, auditable product-creation pipeline that turns a **validated
opportunity** into a concrete, persisted product package:

```
VALIDATED OPPORTUNITY
  → PRODUCT SPECIFICATION       (ProductSpecification — versioned, bounded)
  → PRODUCT GENERATION          (deterministic, clearly labeled MOCKED)
  → CONTENT / ASSET GENERATION  (features, deliverables, usage, assets)
  → QUALITY VALIDATION          (deterministic Product Quality Gate)
  → HALAL / SAFETY VALIDATION   (EXISTING halal filter — no second system)
  → LANDING PAGE GENERATION     (ProductLandingPage — non-payment CTA)
  → PRODUCT PACKAGE             (ProductVersion — history preserved)
  → READY_FOR_PUBLISHING        (spec record; lifecycle READY_TO_DEPLOY)
```

## Authority boundaries (unchanged)

- **Product.status** is mutated ONLY by the guarded lifecycle machine
  (`lifecycle-service.applyProductTransition`). The pipeline maps onto the
  existing transitions: `VALIDATE → SPEC_READY → BUILD → START_TESTING →
  TEST_PASS` (ending at `READY_TO_DEPLOY`, the lifecycle's "ready for the next
  external gate"). Failures map to `TEST_FAIL` (→ BUILDING) or `BLOCK`.
- **The Job Runner is authoritative for execution.** The Income Engine's BUILD
  stage dispatches `PRODUCT_CREATE { opportunityId }`; the job layer runs the
  full pipeline inside the existing idempotency/halal gates. Duplicate
  correlation ids are deduplicated by the Job Runner; duplicate pipeline
  dispatches are deduplicated or versioned (never silently duplicated).
- **Safety** reuses `screenForHalalCompliance`. This is an automated screening
  control mechanism, NOT a religious ruling. `NOT_ALLOWED` blocks (product →
  BLOCKED, no landing page); `REVIEW_REQUIRED` pauses for a qualified human.

## Product states

Pipeline-level status lives on `ProductSpecification.status`:

| Status | Meaning |
|---|---|
| `DRAFT` | Spec row created |
| `GENERATING` | Deterministic generation in progress |
| `GENERATED` | Content generated; artifact under construction |
| `VALIDATING` | Quality gate + safety screening in progress |
| `READY_FOR_PUBLISHING` | All gates passed; package complete |
| `QUALITY_FAILED` | Deterministic gate failed (reasons persisted per gate) |
| `SAFETY_FAILED` | Automated safety screening blocked the product |
| `FAILED` | Lifecycle machine did not confirm the final transition |

The guarded lifecycle machine on `Product` remains the authoritative product
state (`IDEA → VALIDATED → SPEC_READY → BUILDING → TESTING →
READY_TO_DEPLOY`).

## Quality gate (deterministic)

`runProductQualityGate` checks: required fields, content completeness (≥3
sections with points), feature/deliverable/usage completeness, opportunity
reference, provenance + correlation id, JSON well-formedness, placeholder
junk, accidental secrets, unsupported market claims ("guaranteed", "risk-free",
"income claims" — market evidence is recorded as `UNAVAILABLE`), fabricated
testimonials/social proof, version consistency, and artifact existence. Every
gate records a human-readable reason; failures are persisted for diagnosis.

## Versioning

Each pipeline run on a non-ready product creates a NEW `ProductSpecification`
version (v+1) and a `ProductVersion` history row with a changelog. Previous
versions are preserved verbatim. An already-`READY_FOR_PUBLISHING` product is
returned as-is (deduplicated stage recorded), never regenerated.

## Generation modes

Content is generated by the deterministic adapter (bound, control-char-safe,
derived only from the opportunity record). Provenance is `MOCKED` /
`DETERMINISTIC` — never presented as live AI output or verified data. When an
AI provider key is configured later, generation may be upgraded behind the
same boundary without changing the gate, lifecycle, or job contracts.

## Security considerations

No new inputs cross the trust boundary: spec fields derive from persisted
opportunity records and are control-char-stripped and length-capped at the
boundary. The gate scans generated content for secrets, market claims, and
fabricated social proof. No credentials are read, logged, or persisted; no
raw SQL; no new external calls. All existing security controls (auth, rate
limiting, CSRF/origin, body caps, CSP) are untouched.

## Business Manager routing integration

The Business Manager's decision tree now branches on the REAL product-pipeline
state (`ProductSpecification` + `Product` records, via the pure resolvers
`resolveProductPipelineState` / `selectRoutingPipelineState` in
`src/lib/product-factory/pipeline.ts`). Spec lookup failure degrades to absent
state — never fabricated:

- `READY_FOR_PUBLISHING` → `CONNECT_PUBLISHING` (new `ActionType`). The
  creation pipeline finished all canonical stages; the publishing capability
  stays NOT_CONFIGURED until an authorized provider is connected and a human
  approves. `executionEligible` is `false` — publishing is never autonomous.
- `BLOCKED` / `SAFETY_FAILED` → `HUMAN_REVIEW`. The safety gate stopped the
  product; no autonomous work resumes.
- `IN_PROGRESS` / `QUALITY_FAILED` → `BUILD_PRODUCT` (execution-eligible).
  Re-running the deterministic pipeline through the Job Runner
  (`PRODUCT_CREATE` with the `opportunityId`) resumes with a new spec version.
- `NOT_STARTED` (legacy product, no Phase B spec) → `IMPROVE_PRODUCT`
  (unchanged behavior).

The canonical stage contract is `PRODUCT_PIPELINE_STAGES`:
`PRODUCT_SPECIFICATION → PRODUCT_GENERATION → CONTENT_ASSET_GENERATION →
QUALITY_VALIDATION → HALAL_SAFETY_VALIDATION → LANDING_PAGE_GENERATION →
PRODUCT_PACKAGE → READY_FOR_PUBLISHING`. Each stage maps onto the guarded
lifecycle machine (`VALIDATE → SPEC_READY → BUILD → START_TESTING →
TEST_PASS → READY_TO_DEPLOY`), and the JobRun summary records the named stage
trace for auditability. Pipeline state also appears in the BM result as
`VERIFIED_DATA` evidence sourced from `db.productSpecification`.
