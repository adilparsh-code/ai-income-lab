# AI Income Lab — Database & Prisma Operations

This is the operator reference for the PostgreSQL layer: which CLI is
authoritative, which environment variables are required, how the migration
history is verified **without** credentials, and the exact one-time action
needed to verify the migrations against a real database.

## 1. Toolchain (what actually runs)

| Concern | Authoritative | Notes |
| --- | --- | --- |
| Schema | `prisma/schema.prisma` | `datasource db { provider = "postgresql" }` — never change the provider. |
| CLI for migrations | **Prisma 7** (`@prisma/prisma7`, pinned `7.10.0`) | Invoked as `npx prisma7 …` by every npm script. |
| CLI config for migrations | **`prisma7.config.ts`** | Loads `.env.local` then `.env`, passes `DIRECT_URL` (falling back to `DATABASE_URL`) as the datasource URL. |
| Runtime client | `@prisma/client` + `@prisma/adapter-pg` | Used through the lazy proxy in `src/lib/db.ts` with `DATABASE_URL`. |
| Test client | `prisma/schema.test.prisma` → `prisma/test-client/` | Generated by `scripts/generate-test-schema.mjs` (`provider = "sqlite"`); hermetic tests only. |

`prisma.config.ts` + `prisma8/contract.prisma` are the **Prisma 8 preview**
surface (`npm run prisma8:emit`). They are not used for migrations and must not
replace the Prisma 7 migration path.

`npm install` / CI run `postinstall` → `prisma7 generate` (no database needed)
and the SQLite test-schema generator.

## 2. Required environment variables

Set these in `.env.local` (git-ignored) for local work and in the deployment
platform's secret store for production. `.env.example` documents them with
placeholders only.

| Variable | Used by | Purpose |
| --- | --- | --- |
| `DATABASE_URL` | App runtime (`src/lib/db.ts`, `@prisma/adapter-pg`) | Application connection. In production: Supabase **transaction** pooler, port `6543`. |
| `DIRECT_URL` | `prisma7` CLI (`migrate status`, `migrate deploy`) | Direct/session connection, port `5432`. PgBouncer on `6543` rejects the CLI engine's prepared statements. Falls back to `DATABASE_URL`. |

Without them:

- `prisma7 generate`, `prisma7 validate`, the drift check, typecheck, tests and
  build all still work (they never touch a database).
- `prisma7 migrate status` / `migrate deploy` fail with
  `The datasource.url property is required in your Prisma config file` — that is
  the expected, fail-closed behaviour.
- The app fails fast in production and uses a local SQLite file in development.

No credential is ever printed, logged, or written by any script in `scripts/`.

## 3. Migration history (Prisma 7)

`prisma/migrations/` is the Prisma 7 history applied by `prisma7 migrate deploy`.
`migrations/` (root) is the separate Prisma 8 contract history — do not mix them.

| Migration | Adds |
| --- | --- |
| `0001_init` | Core domain: `Opportunity`, `Product`, `ProductBuild`, `ProductDeployment`, `ProductAsset`, `Experiment`, `Revenue`, `Affiliate`, `Content`, `EvidenceItemModel`, `PipelineRun`, `SecurityEvent`, `RateLimitWindow`, `IntegrationAuthorization`, `JobRun`, `WorkflowRun`, `ProductEvent`, `AgentLog`. |
| `0002_phase8_ops` | Operations layer: `AgentMission`, `LoopTransition`, `SimulationRun`, `OperationalMemory`, `FailureRecord`. |
| `0003_phase9_growth` | Growth/business: `PortfolioItem`, `GrowthExperiment`, `GrowthDecision`, `LearningEntry`, `ResourceAllocation`. |
| `0004_high1_handoff` | `OpportunityHandoff` (inbound handoff contract). |
| `0005_agency_layer` | Agency layer: `AdminSession`, `AgentDefinition`, `AgentRun`, `AgentMessage`, `AgentHealth`, `AgentPermission`, `HumanReview`, `SupervisorEvaluation`, `AgencyControl`. |

Every file is additive (`CREATE TABLE` / `CREATE INDEX` / `ALTER TABLE … ADD
CONSTRAINT`). There is no `DROP`, `TRUNCATE`, `DELETE`, or data-mutating
`UPDATE` in any of them; `npm run prisma:drift-check` enforces that on every CI
run.

## 4. Verification that needs no database

```bash
npm run prisma:validate        # schema is valid Prisma 7
npm run prisma:drift-check     # schema vs prisma/migrations/ (38 models, 0 drift) + destructive-SQL audit
npm run prisma:generate        # regenerate the PostgreSQL client
npm run typecheck              # tsc --noEmit
npm run test                   # hermetic SQLite suite
npm run build                  # next build
```

`prisma:drift-check` (`scripts/check-migration-drift.mjs`) is read-only and
offline. It parses `prisma/schema.prisma` and every `prisma/migrations/*/`
file, then compares tables, columns (type / nullability / default), primary
keys, indexes and foreign keys — plus `ON DELETE` behaviour — and reports any
difference as drift. It exists because the Prisma 7 CLI equivalents
(`migrate diff --from-migrations` / `--from-empty --to-schema`) need either a
shadow database or a configured datasource URL, and therefore cannot run in a
fresh clone or CI. It never writes to a database.

## 5. Operator runbook — verify the migrations against the real database

Everything repository-side is ready. The steps below need the authorized
PostgreSQL/Supabase credentials; they are the **only** remaining work.

1. Create `.env.local` in the repository root (it is git-ignored) containing the
   two real values from the project's authorized database provider:

   ```dotenv
   DATABASE_URL="postgresql://…:…@…pooler.supabase.com:6543/postgres"
   DIRECT_URL="postgresql://…:…@…pooler.supabase.com:5432/postgres"
   ```

   Use the transaction pooler for `DATABASE_URL` (app runtime) and the
   session/direct connection for `DIRECT_URL` (CLI). Copy the shapes from
   `.env.example`; never commit the file.

2. Compare the recorded history with the migration folder — read-only:

   ```bash
   npm run prisma:migrate:status
   ```

   Expected on a clean, up-to-date database: `Database schema is up to date!`
   and all five migrations listed as applied. A pending `0005_agency_layer`
   means the Agency layer has not been deployed yet.

3. If (and only if) migrations are pending, apply them **forward only**:

   ```bash
   npm run prisma:migrate:deploy
   ```

   `migrate deploy` only applies pending migrations; it never resets, never
   drops, and never asks for a shadow database.

4. Confirm connectivity and row counts (read-only, prints no credentials):

   ```bash
   npm run db:health
   ```

5. Confirm the application's own DB layer resolves through the adapter:

   ```bash
   npm run db:verify-layer
   ```

6. Seed the Agency roster/contracts only if the project expects it, using
   `prisma/seed.ts` semantics — it reads `DATABASE_URL` and never prints it.

### Prohibited commands (project policy)

Never run against this repository's database:

- `prisma migrate reset` (drops and recreates)
- `prisma db push` against production
- `DROP DATABASE` / `DROP TABLE` / `DROP COLUMN` / `TRUNCATE`
- any hand-written destructive SQL
- `git push --force`

Any schema change must land as a **new additive migration** generated against a
real database (`npx prisma7 migrate dev --create-only`), reviewed, and applied
with `migrate deploy`.

## 6. Phase 6A / Agency schema coverage — actual state

Verified against `prisma/schema.prisma` and `prisma/migrations/`:

- **Agency layer (Phase 5/Agency, `0005_agency_layer`)** — present and in
  primary-key/index/foreign-key agreement with the schema: `AdminSession`,
  `AgentDefinition`, `AgentRun`, `AgentMessage`, `AgentHealth`,
  `AgentPermission`, `HumanReview`, `SupervisorEvaluation`, `AgencyControl`.
- **Auth persistence** — this codebase authenticates a **single operator**
  through `AdminSession`: `tokenFingerprint String @unique` (only the HMAC
  fingerprint of the cookie token is stored, never the token), `email`,
  `expiresAt` (indexed), `lastSeenAt`, `createdBy`. `src/lib/security/`
  contains the matching regression suite.
- **Multi-tenant `User` / `Session` / `ownerId` models do NOT exist in this
  schema** (no `model User`, no `model Session`, no `ownerId`/`tenantId`
  anywhere in `src/`). Ownership in this codebase is expressed through optional
  `opportunityId` / `productId` / correlation-id columns with `ON DELETE SET
  NULL` or `RESTRICT` behaviour, not per-user rows. Treat any Phase 6A brief
  that assumes `User`/`Session`/`ownerId` as **not delivered** — adding those
  models is a schema change, which requires a new additive migration generated
  against a real database, not an offline edit.
- **Referential behaviour** — all 27 foreign keys are `ON UPDATE CASCADE` with
  either `ON DELETE RESTRICT` (required parent) or `ON DELETE SET NULL`
  (optional parent), matching the optionality of each relation.

## 7. Security posture (audited)

- Raw SQL is limited to parameter-free tagged templates
  (`db.$queryRaw\`SELECT 1\`` in `src/app/api/health/route.ts` and
  `src/lib/ops/dashboard.ts`). `$queryRawUnsafe` / `$executeRawUnsafe` and any
  `${…}` interpolation inside a raw query are banned by
  `src/lib/security/__tests__/security-regression.test.ts` (T5) and fail CI.
- Credential material is never logged: `scripts/db-health.mjs`,
  `scripts/verify-db-layer.mts` and `scripts/apply-baseline.mjs` read
  `.env.local`, parse the URL, and print only non-secret facts (database name,
  role, counts). Errors name the variable only.
- `.gitignore` blocks `.env`, `.env.local`, `.env.*.local`, `*.pem`, `*.key`
  and everything else matching `.env*`; only `.env.example` (placeholders) is
  committable.
